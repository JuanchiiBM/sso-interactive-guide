calculos:
  - enunciado: 'a) Inodo y bloque de datos asignados a cada archivo.'
    campos:
      - { etiqueta: 'Inodo de `c.txt`', respuesta: 21 }
      - { etiqueta: 'Bloque de `c.txt`', respuesta: 103 }
      - { etiqueta: 'Inodo de `d.txt`', respuesta: 23 }
      - { etiqueta: 'Bloque de `d.txt`', respuesta: 104 }
    justificacion: |
      El soft link es un **archivo nuevo**: necesita su propio inodo y su propio bloque de datos.

      | Archivo | Inodo | Tipo | Puntero | Contenido del bloque |
      | --- | --- | --- | --- | --- |
      | `c.txt` | 21 (primer 0 del bitmap) | regular | 103 | `hola` |
      | `d.txt` | 23 (siguiente 0) | soft link | 104 | `/usr/share/c.txt` |

      Estructuras actualizadas:

      - **Bitmap de inodos:** 21 y 23 pasan a 1 (queda todo en 1 del 20 al 24).
      - **Bitmap de bloques:** 103 y 104 pasan a 1.
      - **Contenido del directorio** `/usr/share`: se agregan `c.txt → 21` y `d.txt → 23`.
  - enunciado: 'c) Formato de la dirección lógica (17 bits, hasta 15 volúmenes, fragmentación interna máxima de 1023 bytes).'
    campos:
      - { etiqueta: 'Bits de segmento', respuesta: 4, unidad: bits }
      - { etiqueta: 'Bits de página', respuesta: 3, unidad: bits }
      - { etiqueta: 'Bits de offset', respuesta: 10, unidad: bits }
    justificacion: |
      Formato `| segmento | página | offset |` (segmentación paginada):

      - **Segmento:** un segmento por volumen, hasta 15 → `2^4 = 16 ≥ 15` → **4 bits**.
      - **Offset:** la fragmentación interna máxima es `tamaño de página − 1 = 1023 B` → páginas de
        1 KiB → **10 bits**.
      - **Página:** `17 − 4 − 10 =` **3 bits**.
preguntas:
  - enunciado: 'a) ¿Qué tipo tiene el inodo de `d.txt` y qué guarda su bloque de datos?'
    opciones:
      - texto: 'Tipo regular; su bloque guarda una copia de `hola`'
        explicacion: 'Eso sería una copia del archivo, no un acceso directo.'
      - texto: 'Tipo soft link; su bloque guarda la ruta `/usr/share/c.txt`'
        explicacion: Correcta.
      - texto: 'Tipo soft link; su puntero apunta al bloque 103 de `c.txt`'
        explicacion: 'El soft link no comparte bloques con el original: guarda la ruta en uno propio.'
      - texto: 'No tiene inodo propio: es una entrada de directorio que apunta al inodo 21'
        explicacion: 'Eso es un hard link.'
    correcta: 1
    justificacion: |
      Un **soft link** es un archivo independiente: tiene su **propio inodo** (el 23), de tipo soft
      link, y su contenido es la **ruta** del archivo al que apunta (`/usr/share/c.txt`), guardada en
      su propio bloque de datos (el 104). Si `c.txt` se borra, el link queda roto.
  - enunciado: 'b) ¿Podría el usuario U2 haber realizado las mismas operaciones?'
    opciones:
      - texto: 'Sí: el directorio tiene permiso de lectura para todos'
        explicacion: 'Leer el directorio no alcanza: crear archivos lo modifica (hace falta w).'
      - texto: 'Sí, si U2 pertenece al grupo G1'
        explicacion: 'El grupo tiene `r--`: tampoco puede escribir.'
      - texto: 'No: crear archivos requiere escribir el directorio, y solo el dueño U1 tiene `w`'
        explicacion: Correcta.
      - texto: 'No: solo el dueño de un directorio puede crear soft links en él, aunque tenga permisos'
        explicacion: 'No hay esa regla: lo que importa es el permiso de escritura.'
    correcta: 2
    justificacion: |
      Crear `c.txt` y `d.txt` agrega entradas en `/usr/share`, o sea **escribe el directorio**. Los
      permisos son `rw-r--r--`: solo el **propietario U1** puede escribir. U2 no es el dueño, y tanto
      el grupo como otros tienen solo lectura → **no puede**.

      Para habilitarlo, U1 tendría que dar escritura al grupo G1 (si U2 pertenece a él) o a otros.

Se dispone de un file system UFS donde el usuario "U1" desea crear el archivo `c.txt` con el
contenido "hola" en el directorio `/usr/share`, y un acceso directo de tipo soft link llamado `d.txt`
en el mismo directorio. **Dadas las siguientes estructuras:**

- **Info directorio:** propietario, grupo ⇒ U1, G1
- **Permisos directorio:** `rw-r--r--`

| Contenido directorio (nombre) | Inodo |
| --- | --- |
| a.txt | 20 |
| b.txt | 22 |

| Inodo bitmap | | Block bitmap | |
| --- | --- | --- | --- |
| 20 | 1 | 100 | 1 |
| 21 | 0 | 101 | 1 |
| 22 | 1 | 102 | 1 |
| 23 | 0 | 103 | 0 |
| 24 | 1 | 104 | 0 |

Se pide:

- a) Actualice las estructuras necesarias para reflejar la exitosa creación del archivo y su acceso
  directo. Grafique también los inodos creados (indicando los valores de los atributos: id, tipo;
  sus punteros en uso y contenido de los bloques referenciados).
- b) ¿Podría el usuario "U2" haber realizado las mismas operaciones? ¿Por qué?
- c) Suponga que las estructuras administrativas de cada volumen de UFS montado en el sistema se
  cargan a memoria en segmentos (uno por volumen), a su vez paginados. ¿Cuál sería la estructura de
  la dirección lógica usada si se dedicaran en total 17 bits, se desean poder montar hasta 15
  volúmenes al mismo tiempo y la fragmentación interna máxima sería de 1023 bytes?
