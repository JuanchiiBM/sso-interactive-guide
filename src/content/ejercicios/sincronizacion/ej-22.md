preguntas:
- enunciado: a) ¿Cuál de estos órdenes de ejecución genera un deadlock?
  opciones:
  - texto: B genera un valor; A lo acumula y hace signal(valorLeido) x2; C imprime el acumulado
    explicacion: 'Es una vuelta normal: cada uno encuentra lo que espera.'
  - texto: C da una vuelta y retoma valorLeido; A toma mutexAcum y espera valorGenerado
    explicacion: 'Correcta: A retiene el mutex esperando a B, B espera valorLeido (lo tiene C) y C espera
      el mutex.'
  - texto: A toma mutexAcum antes que nadie y espera valorGenerado hasta que B genere
    explicacion: 'A espera, pero B todavía puede tomar valorLeido y generar: no se traba.'
  - texto: B y C toman los dos valorLeido al arrancar, antes de que A pida mutexAcum
    explicacion: 'B genera y señala valorGenerado: A puede avanzar y devolver valorLeido.'
  correcta: 1
  justificacion: |
    Traza (valores iniciales `mutexAcum = 1, valorGenerado = 0, valorLeido = 2`):

    1. **C**: `wait(valorLeido)` (queda 1), `wait(mutexAcum)`, `printf`, `signal(mutexAcum)` y vuelve a
       `wait(valorLeido)` (queda 0).
    2. **A**: `wait(mutexAcum)` (lo toma) y `wait(valorGenerado)` → **bloqueado**, espera a B.
    3. **B**: `wait(valorLeido)` → **bloqueado** (valorLeido = 0), espera a que A haga signal.
    4. **C**: `wait(mutexAcum)` → **bloqueado**, lo tiene A.

    A espera a B, B espera a A (que es el único que hace `signal(valorLeido)`) y C espera a A: nadie avanza.
    El problema de fondo: **A toma el mutex antes de saber si hay un valor generado**.
- enunciado: b) ¿Dónde hay una condición de carrera sobre una sección crítica?
  opciones:
  - texto: 'Sobre acum: A la modifica mientras C la imprime dentro del mismo printf'
    explicacion: 'A y C acceden a acum con mutexAcum tomado: nunca a la vez.'
  - texto: 'Sobre valorLeido: B y C lo decrementan al mismo tiempo en su wait'
    explicacion: 'wait es atómico: los semáforos no tienen condición de carrera.'
  - texto: 'Sobre ultValor: B puede generar el siguiente mientras A lo lee y lo pone en 0'
    explicacion: 'Correcta: nada impide que B escriba ultValor entre la lectura y el "= 0" de A.'
  - texto: 'Sobre printf: A y C pueden escribir en pantalla a la vez sin coordinarse'
    explicacion: Solo C imprime; A no escribe en pantalla.
  correcta: 2
  justificacion: |
    `valorLeido` arranca en **2**, así que B puede generar **otro** valor antes de que A termine con el
    anterior:

    1. **B**: `wait(valorLeido)`, `ultValor = generarValor()`, `signal(valorGenerado)`, y vuelve a
       `wait(valorLeido)` (pasa: todavía queda uno).
    2. **A**: `wait(mutexAcum)`, `wait(valorGenerado)`, `acum += ultValor`…
    3. …y justo ahí **B** ejecuta `ultValor = generarValor()` mientras A va a hacer `ultValor = 0`.

    `ultValor` es compartida entre A y B y **ningún semáforo la protege** (`mutexAcum` solo lo usan A y C):
    según cómo se intercalen, un valor se pierde o se acumula dos veces. Hay otros órdenes que también lo
    muestran.

Considere el siguiente pseudocódigo en que se ejecutan 3 procesos concurrentemente, sincronizados con semáforos:

<div class="codigo-columnas">

**Proceso A**

```c
while(true) {
  wait(mutexAcum)
  wait(valorGenerado)
  acum += ultValor
  ultValor = 0
  signal(valorLeido) x 2
  signal(mutexAcum)
}
```

**Proceso B**

```c
while(true) {
  wait(valorLeido)
  ultValor = generarValor()
  signal(valorGenerado)
}
```

**Proceso C**

```c
while(true) {
  wait(valorLeido)
  wait(mutexAcum)
  printf(Acumulado: %d, acum)
  signal(mutexAcum)
}
```

</div>

Valores iniciales: `mutexAcum = 1, valorGenerado = 0, valorLeido = 2, acum = 0, ultValor = 0`.

a) Indique un orden de ejecución, línea por línea, para que se genere un deadlock.

b) Indique un orden de ejecución, línea por línea, mostrando que existe una condición de carrera sobre una sección crítica.
