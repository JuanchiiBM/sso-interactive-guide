semaforos:
- nota: |
    Las variables locales `d = 1` y `e = 2` se inicializan antes del `while` y no se muestran en el editor (no son compartidas).
  procesos:
  - nombre: A
    instancias: 1
    codigo: |
      while(TRUE){
        a = a + d;
        d = d * d;
        b = b - d;
      }
  - nombre: B
    instancias: 1
    codigo: |
      while(TRUE){
        b = b * e;
        e = e ^ e;
        a++;
      }
  acciones:
    a = a + d:
      recursos:
      - a
    d = d * d: {}
    b = b - d:
      recursos:
      - b
    b = b * e:
      recursos:
      - b
    e = e ^ e: {}
    a++:
      recursos:
      - a
  tests:
  - tipo: exclusion
    recurso: a
  - tipo: exclusion
    recurso: b
  - tipo: sin-deadlock
  - tipo: todas-ejecutan
  solucion: |
    semaphore mutex_a = 1, mutex_b = 1;

    void A() {
      while(TRUE){
        wait(mutex_a);
        a = a + d;
        signal(mutex_a);
        d = d * d;
        wait(mutex_b);
        b = b - d;
        signal(mutex_b);
      }
    }

    void B() {
      while(TRUE){
        wait(mutex_b);
        b = b * e;
        signal(mutex_b);
        e = e ^ e;
        wait(mutex_a);
        a++;
        signal(mutex_a);
      }
    }
  justificacion: |
    **Regiones críticas:** las líneas que tocan variables compartidas: `a = a + d` y `a++` (sobre `a`),
    `b = b - d` y `b = b * e` (sobre `b`). Las que usan solo `d` o `e` son locales y **no** son región
    crítica.

    Se usa **un mutex por variable compartida** (regla de la cátedra: un mutex por recurso), ambos
    binarios e inicializados en 1. Así A puede estar modificando `a` mientras B modifica `b`.

    Un único mutex para todo también es correcto (los tests pasan), pero serializa de más: A y B no
    podrían trabajar sobre variables distintas al mismo tiempo.

    Ojo con tomar los dos mutex a la vez en orden opuesto en cada proceso: eso sí puede producir
    **deadlock**.
