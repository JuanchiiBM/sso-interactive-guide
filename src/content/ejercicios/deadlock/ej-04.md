  nota: |

  tests:
  - tipo: sin-deadlock
  - tipo: todas-ejecutan
  solucion: |
    semaphore mutex = 1;

    void A() {
      while(TRUE){
        wait(mutex);
        mate = agarrar_mate();
        termo = agarrar_termo();
        signal(mutex);
        preparar(mate);
        cebar(mate,termo);
      }
    }

    void B() {
      while(TRUE){
        wait(mutex);
        termo = agarrar_termo();
        mate = agarrar_mate();
        signal(mutex);
        preparar(mate);
        cebar(mate,termo);
      }
    }
  justificacion: |
    El problema es que cada proceso puede quedarse con **uno** de los dos recursos mientras espera el otro.
    Con un `mutex` alrededor de los dos `agarrar_*`, la toma del mate y del termo pasa a ser **una sola
    operación** respecto del otro proceso: nunca puede pasar que A tenga el mate y B el termo al mismo
    tiempo.

    Si A entra con el mutex y se bloquea esperando algo, es porque B tiene ese recurso **fuera** de la zona
    protegida: B ya tiene los dos, termina de cebar, los devuelve y A sigue. No se forma el ciclo.

    Envolver también `preparar` y `cebar` en el mutex es correcto, pero no hace falta.
preguntas:
- enunciado: ¿Cómo se demuestra que estos procesos pueden caer en deadlock?
  opciones:
  - texto: 'A toma el mate y B el termo; cada uno queda pidiendo el del otro'
    explicacion: 'Correcta: el grafo queda A → Termo → B → Mate → A, un ciclo con recursos de una instancia.'
  - texto: Hay deadlock porque los dos procesos usan el mate dentro de un while(TRUE)
    explicacion: 'Que el ciclo sea infinito no genera deadlock: lo que importa es el orden de los pedidos.'
  - texto: 'Hay deadlock porque preparar(mate) usa el mate sin haber pedido antes el termo'
    explicacion: 'preparar() se ejecuta con los dos recursos ya tomados: no hay espera ahí.'
  - texto: No puede haber deadlock porque los dos procesos piden exactamente los mismos recursos
    explicacion: 'Piden los mismos, pero en orden inverso: eso es justamente lo que habilita la espera
      circular.'
  correcta: 0
  justificacion: |
    Una intercalación que traba: A ejecuta `agarrar_mate()` y B ejecuta `agarrar_termo()`. Ahora A pide el
    termo (lo tiene B) y B pide el mate (lo tiene A):

    ```grafo
    procesos: A, B
    recursos: Mate, Termo
    Mate -> A
    A -> Termo
    Termo -> B
    B -> Mate
    resaltar-ciclo
    ```

    El grafo tiene un **ciclo** y todos los recursos del ciclo tienen **una sola instancia**, así que es
    condición suficiente: **hay deadlock**. Se cumplen las cuatro condiciones de Coffman:

    - **Mutua exclusión:** hay un solo mate y un solo termo.
    - **Retención y espera:** cada uno retiene el recurso que ya tiene mientras espera el otro.
    - **Sin desalojo:** nadie le saca el recurso a otro proceso.
    - **Espera circular:** A espera a B y B espera a A.
- enunciado: b) ¿Qué solución aplica el mecanismo de Prevención sin introducir otro problema?
  opciones:
  - texto: Si no consigue el segundo recurso, suelta el primero y reintenta
    explicacion: 'Rompe retención y espera, pero si los dos lo hacen a la vez se repite siempre: livelock.'
  - texto: Antes de cada pedido, verificar con el algoritmo del banquero que el estado sea seguro
    explicacion: 'Eso es Evasión (predicción), no Prevención: decide en ejecución en vez de impedir una
      condición.'
  - texto: 'Que los dos pidan en el mismo orden (primero el mate y después el termo), así se rompe la espera circular'
    explicacion: 'Correcta: con un orden global de pedidos no puede cerrarse un ciclo (se rompe la espera
      circular).'
  - texto: Dejar que ocurra, detectar el ciclo en el grafo y matar a uno de los dos procesos
    explicacion: 'Eso es Detección y recuperación: el deadlock se permite y después se arregla.'
  correcta: 2
  justificacion: |
    **Prevención** = diseñar el sistema para que alguna de las cuatro condiciones de Coffman **nunca** se
    cumpla. Acá la más barata de romper es la **espera circular**: si se impone un orden global de pedido
    (por ejemplo, siempre el mate antes que el termo), B cambia sus dos primeras líneas y ya no puede pasar
    que cada uno tenga uno y espere el otro.

    - *Soltar y reintentar* también es prevención (ataca retención y espera / permite el "auto-desalojo"),
      pero sin coordinación puede producir **livelock**: los dos sueltan y vuelven a agarrar al mismo tiempo
      (es el segundo escenario del Ej. 3).
    - *Banquero* es **evasión**; *detectar y matar* es **detección y recupero**.
