  tests:
  - tipo: sin-deadlock
  - tipo: todas-ejecutan
  solucion: |
    semaphore mutex = 1;

    void Proceso() {
      while(TRUE){
        t_buffer rec_id[3] = get_recursos();
        wait(mutex);
        syscall_pedir(rec_id[0]);
        syscall_pedir(rec_id[1]);
        syscall_pedir(rec_id[2]);
        signal(mutex);
        usar_recursos(rec_id);
        syscall_devolver(rec_id[0]);
        syscall_devolver(rec_id[1]);
        syscall_devolver(rec_id[2]);
      }
    }
  justificacion: |
    **Por qué hay deadlock:** los recursos son de una instancia, se piden **de a uno reteniendo** los ya
    obtenidos (retención y espera), nadie se los saca a otro (sin desalojo) y, como el orden es al azar,
    P1 puede tener R0 y esperar R1 mientras P2 tiene R1 y espera R0 (**espera circular**).

    **Prevención con semáforos:** un `mutex` alrededor de los **tres pedidos** hace que la toma de los tres
    recursos sea atómica respecto de los demás procesos. Si un proceso con el mutex se bloquea en un
    `syscall_pedir`, es porque otro tiene ese recurso **fuera** de la zona de pedidos: ese otro ya tiene
    todo lo que necesita, va a usar y devolver sin pedir el mutex, y no se puede cerrar un ciclo.

    Se rompe la **espera circular**. Envolver también `usar_recursos` en el mutex funciona, pero serializa
    de más.
preguntas:
- enunciado: a) ¿Por qué estos procesos pueden quedar en deadlock?
  opciones:
  - texto: Porque hay más procesos que recursos y alguno siempre tiene que esperar a que se libere uno
    explicacion: 'Esperar no es deadlock: con más procesos que recursos igual todos terminan si no hay
      ciclo.'
  - texto: 'Porque piden de a uno, en orden al azar y reteniendo: dos pueden esperar el recurso del otro'
    explicacion: 'Correcta: P1 con R1 esperando R2 y P2 con R2 esperando R1 cierra un ciclo.'
  - texto: Porque syscall_devolver() se llama en el mismo orden en que se pidieron los recursos
    explicacion: 'El orden de devolución no genera espera: devolver nunca bloquea.'
  - texto: Porque usar_recursos() se ejecuta sin exclusión mutua entre los N procesos que corren
    explicacion: 'Cada recurso tiene una instancia y ya está tomado por quien lo usa: no hay condición
      de carrera.'
  correcta: 1
  justificacion: |
    Ejemplo con dos procesos y recursos R1, R2, R3:

    1. P1 obtiene `rec_id = [R1, R2, R3]` y P2 obtiene `rec_id = [R2, R1, R3]`.
    2. P1 pide R1 (lo obtiene) y P2 pide R2 (lo obtiene).
    3. P1 pide R2 → bloqueado (lo tiene P2). P2 pide R1 → bloqueado (lo tiene P1).

    ```grafo
    procesos: P1, P2
    recursos: R1, R2
    R1 -> P1
    P1 -> R2
    R2 -> P2
    P2 -> R1
    resaltar-ciclo
    ```

    Se cumplen las cuatro condiciones: una sola instancia por recurso (**mutua exclusión**), cada uno
    retiene lo que tiene mientras pide el resto (**retención y espera**), nadie se los quita (**sin
    desalojo**) y el orden al azar permite el ciclo (**espera circular**).
- enunciado: c) Sin semáforos ni cambiar syscall_pedir(), ¿cómo se previene el deadlock?
  opciones:
  - texto: Devolver los recursos en el orden inverso al que se pidieron, del último al primero
    explicacion: 'El orden de devolución no importa: el ciclo se forma durante los pedidos.'
  - texto: Pedir los recursos exactamente en el orden en que los devuelve get_recursos()
    explicacion: 'Es lo que ya hace el código: como ese orden es al azar, la espera circular sigue siendo
      posible.'
  - texto: Que get_recursos() no repita ids
    explicacion: 'Los ids ya son distintos: repetirlos no es lo que causa el deadlock.'
  - texto: 'Ordenar rec_id de menor a mayor antes de pedir los recursos, así todos piden en un mismo orden global'
    explicacion: 'Correcta: con un orden global de pedidos no puede cerrarse un ciclo de espera.'
  correcta: 3
  justificacion: |
    Es **prevención por eliminación de la espera circular**: se define un orden total entre los recursos
    (sus ids) y todos los procesos los piden en ese orden. Si P1 espera un recurso que tiene P2, ese
    recurso tiene un id **mayor** que todos los que P1 ya tiene; para que P2 esperara algo de P1 haría
    falta un id **menor**, y P2 nunca pide para atrás. No se puede cerrar el ciclo.

    Solo hace falta agregar un ordenamiento de `rec_id` después de `get_recursos()`: las llamadas a
    `syscall_pedir()` quedan igual.

Se encuentran N procesos compartiendo distintos recursos, de los cuales existe una sola instancia de cada uno, ejecutando el siguiente código:

**Proceso A (N instancias)**

```c
variable_local d = 1;
while(TRUE){
  t_buffer rec_id[3] = get_recursos(); // devuelve aleatoriamente tres IDs de recursos
  syscall_pedir(rec_id[0]); // Bloqueante si el recurso no se encuentra disponible.
  syscall_pedir(rec_id[1]);
  syscall_pedir(rec_id[2]);
  usar_recursos(rec_id);
  syscall_devolver(rec_id[0]);
  syscall_devolver(rec_id[1]);
  syscall_devolver(rec_id[2]);
}
```

- a. Demuestre que dichos procesos podrían quedar en deadlock.
- b. Proponga una solución para prevenir el deadlock, usando semáforos.
- c. Considere las condiciones necesarias y suficientes para la existencia de deadlock y proponga una solución para prevenirlo sin usar semáforos ni modificar las llamadas syscall_pedir().
