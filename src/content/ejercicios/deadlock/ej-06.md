  solucion: |
    semaphore CS = 1, C = 1, A = 0, S = 0;

    void C() {
      while(TRUE){
        wait(C);
        wait(CS);
        print("C");
        signal(A);
        signal(S);
      }
    }

    void A() {
      while(TRUE){
        wait(A);
        print("A");
        signal(CS);
      }
    }

    void S() {
      while(TRUE){
        wait(S);
        wait(CS);
        print("S");
        signal(A);
        signal(C);
      }
    }
  justificacion: |
    **Por qué se traba el original:** C y S hacen `wait(CS)` **antes** de esperar su turno. Después de
    "CA", A devuelve `CS`; si C lo toma primero, se queda esperando `C` (que vale 0) **con `CS`
    retenido**, y S queda esperando `CS`. A espera `A`. Nadie puede avanzar: hay **retención y espera**
    y **espera circular** sobre `CS`.

    **Corrección:** esperar primero el semáforo de turno (`C` o `S`) y recién después `CS`. Así solo
    toma `CS` el proceso al que efectivamente le toca, y se rompe la condición de retención y espera.
    Es la regla de la cátedra: **el orden de los `wait` importa**.
preguntas:
- enunciado: a) ¿Cuál de estas secuencias de ejecución lleva a deadlock?
  opciones:
  - texto: Al arrancar, A hace wait(A) antes que los demás y queda esperando a que C imprima
    explicacion: 'A se bloquea, pero C sigue pudiendo avanzar: no es deadlock, es la espera normal.'
  - texto: C imprime C y A imprime A; después S hace wait(CS) y wait(S) e imprime S
    explicacion: 'Esa es la secuencia correcta: A devolvió CS y S tiene su turno habilitado.'
  - texto: Al arrancar, S hace wait(CS) antes que C y se bloquea en wait(S)
    explicacion: 'Correcta: S retiene CS esperando S (vale 0), C espera CS y A espera A. Nadie avanza.'
  - texto: C imprime C; antes de que A imprima, S hace wait(CS) y queda esperando que se libere
    explicacion: 'S espera CS, pero A lo va a devolver después de imprimir: S sigue sin problema.'
  correcta: 2
  justificacion: |
    Valores iniciales: `CS = 1, C = 1, A = 0, S = 0`. Si **S** es el primero en ejecutar:

    1. `wait(CS)` → CS = 0: S toma el turno compartido.
    2. `wait(S)` → S vale 0: **S se bloquea con CS tomado**.
    3. C hace `wait(CS)` → se bloquea (lo tiene S).
    4. A hace `wait(A)` → se bloquea (nadie hizo `signal(A)`).

    Los tres quedan bloqueados para siempre: deadlock. La misma trampa aparece más adelante: después de
    "CA", si C vuelve a tomar `CS` antes que S, queda esperando `C` con `CS` retenido.

    El problema de fondo: C y S **toman `CS` antes de saber si les toca** (retención y espera).
- enunciado: b) Sin modificar el código, ¿cómo se previene el deadlock?
  opciones:
  - texto: Que el SO otorgue CS y el turno propio juntos, o ninguno
    explicacion: 'Correcta: si no se puede retener CS esperando el turno, se rompe retención y espera.'
  - texto: Correr periódicamente un algoritmo de detección y reiniciar los procesos trabados
    explicacion: 'Eso es Detección y recuperación: el deadlock ocurre y después se arregla.'
  - texto: Antes de cada wait, simular si el estado resultante es seguro (algoritmo del banquero)
    explicacion: 'Eso es Evasión: evalúa cada pedido en ejecución en vez de eliminar una condición.'
  - texto: Dar más prioridad al proceso A para que siempre ejecute antes que C y que S
    explicacion: 'La prioridad no cambia qué retiene cada uno: S puede seguir tomando CS antes que C.'
  correcta: 0
  justificacion: |
    **Prevención** elimina una de las condiciones de Coffman. Sin tocar el código, la que se puede atacar
    es **retención y espera**: si el SO asigna los dos semáforos que necesita cada proceso (`CS` y su
    turno) **en una sola operación atómica**, un proceso nunca queda con `CS` tomado esperando `C` o `S`.
    O los consigue los dos y avanza, o no toma ninguno.

    En el inciso (c) se resuelve cambiando el código: esperar primero el turno y después `CS`.
